# SISM 提交与分支工作流（定稿）

> 定稿日期：2026-10-26
> 适用范围：`sism-backend`、`strategic-task-management` 两个仓库，规则完全一致。
> 本文是**唯一权威**的分支/提交规则。`COMMIT_CONVENTION.md` 只描述提交信息格式，分支规则以本文为准。

## 0. 铁律（不再讨论）

1. **只保留两个长期分支**：`main` 与 `develop`。其余分支一律短生命周期，合入即删。
2. **GitHub 只做构建**。CI 产出 artifact + 推 GHCR，**不得**在任何 workflow 里下载产物到服务器、执行 `docker load`、`docker compose up`，也不得触发另一个仓库的部署 workflow。
3. **落服只能走本地三步**：`download-offline-release.sh` → `upload-offline-release.sh` → `install-offline-release.sh`。
4. **不在 `main` 上直接写代码**；`main` 只接受来自 `develop`（或 `hotfix/*`）的合并。
5. **每个改动的分支必须在合并后 24 小时内删除**，不允许出现「改完了但分支还挂着」的状态。

## 1. 分支模型

| 分支 | 生命周期 | 从哪拉 | 合到哪 | 保护 |
|---|---|---|---|---|
| `main` | 永久 | — | — | 受保护，禁止直推 |
| `develop` | 永久 | `main` | `main`（发布时） | 建议保护，允许管理员直推 |
| `feature/<slug>` | 短 | `develop` | `develop` | 无 |
| `fix/<slug>` | 短 | `develop` | `develop` | 无 |
| `hotfix/<slug>` | 短 | `main` | `main` + 回灌 `develop` | 无 |
| `chore/<slug>` `docs/<slug>` `ci/<slug>` | 短 | `develop` | `develop` | 无 |
| `release/vX.Y.Z` | 仅冻结期 | `develop` | `main` | 无，发版后立刻删 |

`<slug>` 用小写连字符，一句话说清改动，例如 `fix/approval-label-per-tab`、`feat/role-org-scope`。

**已废止**：`baseline/*`、`test/*`、`dev/*`、长期 `fix/*` 堆积。历史内容已转为 `archive/*` 标签留档。

## 2. 提交信息

格式：

```text
<type>(<scope>): <summary>

<body 可选，说明动机与影响>

<footer 可选，如 Refs #123 / BREAKING CHANGE: ...>
```

**type 白名单**：`feat` `fix` `refactor` `perf` `test` `docs` `chore` `ci` `build` `style`

**scope 建议值**（后端）：`authz` `approval` `plan` `task` `indicator` `report` `alert` `db` `deploy` `ci`
**scope 建议值**（前端）：`approval` `plan` `task` `indicator` `report` `router` `store` `ui` `build`

规则：

- summary 一行、祈使句、不超过 72 字符，描述**实际改动**而非意图。
- 不相关改动拆成多个 commit；基础设施/部署改动尽量与业务逻辑分开提交。
- 提交信息里不写「未合并的 PR 当作已合并」这类表述；状态以 GitHub 实际为准。

## 3. 一次改动的完整生命周期

```bash
# ① 起点必须是干净的 develop
git checkout develop && git pull --ff-only

# ② 拉短分支
git checkout -b fix/approval-label-per-tab

# ③ 本地验证（后端）
./mvnw -B clean verify
#    本地验证（前端）
npm run lint:check && npm run type-check && npm run build

# ④ 提交
git add -A && git commit -m "fix(approval): 头部状态标签按页签动态显示"

# ⑤ 推送并开 PR（目标 develop）
git push -u origin fix/approval-label-per-tab
gh pr create --base develop --fill

# ⑥ CI 绿 → squash 合并
gh pr merge --squash --delete-branch

# ⑦ 本地同步并删掉自己的分支引用
git checkout develop && git pull --ff-only && git branch -d fix/approval-label-per-tab
```

**合并策略**：

- `feature/*` `fix/*` `chore/*` → `develop`：**squash merge**（历史干净，一个改动一个 commit）
- `develop` → `main`：**`git merge --no-ff`**（保留一条可识别的发布合并点）

## 4. 发布与打标签

```bash
# develop 通过验收后
git checkout main && git pull --ff-only
git merge --no-ff develop -m "chore(release): 合并 develop 到 main —— <一句话概括>"
git push origin main
# → 触发两仓 CI + 镜像构建（推 GHCR，产出 artifact），到此为止，不落服

# 需要留发布点时
git tag -a v1.2.0 -m "v1.2.0" && git push origin v1.2.0
```

发布后：`develop` 若落后于 `main`，用 `git checkout develop && git merge --ff-only main` 快进对齐。

## 5. 分支清理纪律

- 每个 PR 合并时**必须**勾选 delete branch（`gh pr merge --delete-branch`）。
- 每月运行一次审计脚本：

```bash
cd backend && ./scripts/git/branch-audit.sh          # 只读，列出三类分支
cd backend && ./scripts/git/branch-audit.sh --apply  # 执行清理
```

脚本的三类判定：

| 类别 | 判定 | 处理 |
|---|---|---|
| A 已合入 main | `merge-base --is-ancestor` 成立 | 直接删 |
| B 补丁等价 | `git cherry` 无 `+` 行（内容已通过 squash 进 main） | 直接删 |
| C 有独有提交 | `git cherry` 存在 `+` 行 | **先打 `archive/<repo>/<branch>` 标签**再删 |

- `archive/*` 标签是只读留档，不再作为工作分支；需要时可 `git switch -c <new> archive/<repo>/<branch>` 复活。
- 严禁为了「留一手」而保留一堆半成品分支——那是仓库变乱的唯一原因。

## 6. 禁做清单

- ❌ 在 `main` 上直接 commit
- ❌ 从 `main` 拉 `feature/*`（除 `hotfix/*`）
- ❌ 给 workflow 加 `workflow_dispatch` 的部署参数、或加 `self-hosted` runner 任务
- ❌ 在服务器上 `docker pull` 镜像（跨境 38 KB/s，实测 168 MB 需 75 分钟）
- ❌ 合并后不删分支
- ❌ 把 `archive/*` 标签当分支用
