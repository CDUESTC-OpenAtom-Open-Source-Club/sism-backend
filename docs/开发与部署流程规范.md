# SISM 开发与部署流程规范

> 最后更新：2026-10-26（**拓扑定死**：GitHub 只构建，落服只走本地三步）
> 适用：`sism-backend`、`strategic-task-management`
> 分支与提交规则见 `docs/提交与分支工作流.md`（唯一权威）

## 1. 拓扑（定死，不再有第二种做法）

```text
本地开发 ──push──▶ GitHub Actions（构建 + 推 GHCR + 产出 artifact）
                              │
                              │  ❌ 不再往服务器推
                              ▼
                     本地 Mac：download-offline-release.sh
                              │  （跨境下行 1.26 MB/s）
                              ▼
                     本地 Mac：upload-offline-release.sh
                              │  （上行到服务器 5.6 MB/s）
                              ▼
                     服务器：install-offline-release.sh（校验→装镜像→compose up→健康检查→失败回滚）
```

**为什么不让服务器自己拉**（2026-10-27 实测数据）：

| 链路 | 实测速率 | 168 MB 产物耗时 |
|---|---|---|
| 服务器 → GitHub 产物存储 | 38 KB/s | 约 75 分钟 |
| Mac → GitHub 产物存储 | 1.26 MB/s | 约 2.5 分钟 |
| Mac → 服务器（ssh/scp） | 5.6 MB/s | 42 秒 |

服务器走跨境线路，直接在服务器上下载产物会让一次部署卡一个多小时。**产物必须先落到本地，再由本地推送。**

## 2. GitHub 侧职责（只做这些）

| 工作流 | 文件 | Job | 干什么 |
|---|---|---|---|
| Build and Push Backend | `backend/.github/workflows/build-and-push-image.yml` | `qa` → `prepare-deployment` → `build-and-push` | 编译验证、打包 compose/seed、构建镜像推 GHCR、上传 `backend-image-<sha>` 与 `backend-stack-<sha>` |
| Build and Push Frontend Image | `frontend/.github/workflows/build-and-push-image.yml` | `qa` → `build-and-push` | 前端质量门、构建镜像推 GHCR、上传 `frontend-image-<sha>` |
| CI / Frontend CI | `ci.yml` | 各自 | PR 与 develop 的校验 |
| Deployment Portability | `deployment-portability.yml` | 宿主契约探针 | 在 GitHub 托管 runner 上验证 compose 能否 load & boot |

**硬约束**：

- 所有 job 都跑在 GitHub 托管 runner（`ubuntu-24.04`）上，**不允许出现 `self-hosted`**。
- workflow 里不允许出现 `docker load` 到生产目录、`docker compose up`、`actions/download-artifact` 下载镜像到服务器、跨仓 `dispatches` 触发部署。
- 校验命令（两仓都跑一遍，输出必须为空）：

```bash
grep -rnE "self-hosted|docker compose up|download-artifact" .github/workflows/
```

## 3. 免费额度纪律

GitHub Actions 对私有仓库按分钟计费。省额度的做法：

- **只在 `main` 上触发构建**（push 到 main 才构建镜像）；`develop` 只跑 CI 校验。
- **不要为「看看能不能跑」而手动 dispatch** 构建工作流——一次完整后端构建约 1.5 分钟（QA 0.5 + 构建 1 分钟），前端约 3 分钟。
- 部署**完全不消耗** GitHub 额度（在本机执行）。
- 确需手动重建时：`gh workflow run build-and-push-image.yml --ref main`，用完即止。

## 4. 发布流程（develop → main → 离线落服）

```bash
# ① 合并发版
git checkout main && git pull --ff-only
git merge --no-ff develop -m "chore(release): 合并 develop 到 main —— <概括>"
git push origin main
#    → 两仓自动触发构建（不落服）

# ② 等两仓构建 success
gh run list --limit 3          # 取 backend 的 run id
gh run list --limit 3          # frontend 仓库同理

# ③ 本地组装离线包（约 8 分钟，含 192 MB 下载）
cd backend/scripts/deployment
./download-offline-release.sh --output ../../out/offline-releases \
  --backend-run <backend_run_id> --frontend-run <frontend_run_id>

# ④ 上传并远端校验（约 42 秒）
./upload-offline-release.sh \
  --archive ../../out/offline-releases/sism-offline-<bsha12>-<fsha12>.tar.gz \
  --remote root@175.24.139.148 --upload-only

# ⑤ 落服（服务器上执行，含健康检查与失败回滚）
ssh root@175.24.139.148 \
  'bash /opt/sism-releases/sism-offline-<bsha12>-<fsha12>/scripts/install-offline-release.sh \
   --target /opt/sism-stack/production'
```

**部署安全三道门**：

1. 构建与落服物理分离：GitHub 侧根本没有能碰服务器的 job。
2. 产物必须经过 `sha256` 逐文件校验（`upload-offline-release.sh` 自动做，输出 `BUNDLE_VERIFIED`）。
3. `install-offline-release.sh` 内置健康检查，失败时自动把 `BACKEND_IMAGE`/`FRONTEND_IMAGE` 回滚到旧值并重建。

## 5. 回滚

```bash
ssh root@175.24.139.148
cd /opt/sism-stack/production
grep -E '^(BACKEND_IMAGE|FRONTEND_IMAGE)=' .env      # 看当前指向
# 手工回滚：把两个 IMAGE 改回上一个 sha，然后
docker compose -f docker-compose.yml up -d --force-recreate
```

历史镜像 tag 均以 commit sha 保留，`docker images | grep sism-backend` 可见。

## 6. 热修复（hotfix）

```bash
git checkout main && git pull --ff-only
git checkout -b hotfix/xxx          # 从 main 拉，不是 develop
# 修复 + 本地验证 + 提交 + PR 回 main（触发构建）
# 落服走第 4 节 ③④⑤
# 修复合回 develop，防止下次发版丢失：
git checkout develop && git merge --ff-only main
```

## 7. 首次部署 / 空库部署

- Flyway 含 `V84.1` 空库引导迁移（幂等补齐组织/角色/权限/管理员/审批链最小数据）
- `spring.flyway.out-of-order: true` 已开启（历史库在 V98 后允许低版本乱序补执行）
- `V84.1` 的 5 条 INSERT 全部 `ON CONFLICT (id) DO NOTHING`，对非空生产库幂等
- 服务器数据库为空时自动灌入基础种子；已有数据不受影响
