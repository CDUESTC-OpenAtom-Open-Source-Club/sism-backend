# SISM 开发与部署流程规范

> 最后更新：2026-10-26（确立三角分支模型与离线部署标准路线）
> 参考业界成型实践：GitHub Flow + 环境分支（develop 集成线）的简化变体，适配「服务器与 GitHub 网络不通」的离线约束。

## 1. 分支模型（三角模型）

| 分支 | 定位 | 保护 |
|---|---|---|
| `main` | **最新稳定版**。每次合并都触发 CI + 镜像构建（推 GHCR），**不自动部署** | 只接受 PR 合并 |
| `develop` | **开发中的迭代线**。日常小功能/小界面改动在这里提交，push 自动跑 CI 校验 | 只接受 PR 或直推（团队规模小，直推允许） |
| `feature/*` `fix/*` | 短生命周期分支。从 develop 拉，验收后 PR 回 develop | 用完即删 |

**关键规则**：
- **不在 main 上直接开发**；main 只从 develop 合并
- **修复一律走 PR**（不再堆 fix/* 长期分支）
- `baseline/*` 为历史快照留档，不再作为工作分支

## 2. 日常开发流程（本地）

```bash
# 1) 从 develop 拉特性分支
git checkout develop && git pull
git checkout -b feature/xxx

# 2) 开发 + 本地验证
#    前端：npm run lint:check && npm run type-check && npm run arch:check && npm run build
#    后端：./mvnw test && ./mvnw -DskipTests package

# 3) 提交并推送特性分支（CI 自动校验）
git push origin feature/xxx

# 4) 验收通过 → PR 合并回 develop
```

## 3. 发布流程（develop → main → 部署）

```bash
# 1) develop 验收后合并到 main
git checkout main && git pull
git merge --no-ff develop
git push origin main
#    → 自动触发：CI 校验 + 镜像构建 + 推 GHCR（不落服）

# 2) 等 Actions 两个仓库构建 success（frontend + backend）
```

## 4. 部署（三选一，按场景）

| 方式 | 命令/操作 | 适用 |
|---|---|---|
| **A 离线三步（推荐，标准路线）** | 见下 | 服务器与 GitHub 不通（当前常态） |
| B Workflow 在线部署 | Actions 页手动 Run `build-and-push-image.yml`，选 `delivery_target=test-server` + `deploy_mode=full-stack` | 服务器 self-hosted runner 可用且线路良好 |
| C 不部署 | 什么都不做 | 代码进 main 即可，镜像已在 GHCR 备用 |

**A 离线三步（标准路线）**：

```bash
cd backend/scripts/deployment
./download-offline-release.sh              # ① 本地拉取产物，组装离线包
./upload-offline-release.sh --archive <包.tar.gz> --remote root@47.108.249.115   # ② 上传
# 服务器上：
./install-offline-release.sh --target /opt/sism-stack/production   # ③ 校验→落服→健康检查→失败自动回滚
```

**部署安全三道门**：
1. push main 只构建镜像，Deploy job 需 `workflow_dispatch` + 显式选 `test-server`
2. 产物落地靠人工搬运（服务器与 GitHub 不通）
3. `install-offline-release.sh` 内置健康检查与失败自动回滚

## 5. 热修复（hotfix）

生产发现紧急问题：
```bash
git checkout main && git pull
git checkout -b hotfix/xxx     # 从 main 拉（不是 develop）
# 修复 + 验证 + 提交 + 推送
# PR 回 main（触发构建）→ 部署 → 同时把修复合回 develop（防止下次发版丢失）
```

## 6. 首次部署 / 空库部署

- Flyway 迁移含 `V84.1` 空库引导迁移（幂等补齐组织/角色/权限/管理员/审批链最小数据）
- `spring.flyway.out-of-order: true` 已开启（历史库在 V98 后允许低版本乱序补执行）
- 服务器数据库为空时自动灌入基础种子；已有数据不受影响
